# 开发指南

当前先做本机软件开发，不连接板子。实际证据见 [acceptance.md](acceptance.md)，首切片接口见 [002-control-api.md](specs/002-control-api.md)。以下命令在首切片分支 `feat/group-control` 运行；仅文档分支尚不包含 `server/`。切换前先保存自己的工作，或使用独立工作树。代码 PR 提供合并和验证入口。

## 启动控制流程演示

需要 Go 和 Node.js（Node 仅用于浏览器状态测试）。服务端使用标准库，不需要七牛 Key、外部模型、数据库或 ESP-IDF。

从仓库根目录执行：

```sh
cd server
go run ./cmd/intercom
```

打开[本机页面](http://127.0.0.1:8080)。默认状态写在仓库 `work/intercom/state.json`，已忽略；Token、群口令不应贴进日志或 Git。可通过 `-addr` 和 `-data` 指定监听与数据文件。默认本机地址应保持到局域网部署切片补齐访问控制为止。

用两个独立浏览器配置或普通/隐私窗口分别创建身份：A 建立“全员群”并分享口令，B 加入；A 再建立“后勤组”，验证当前群仍为全员群。B 输错口令不加入；两端同时按住控制按钮仅一端获权。手动切群后原麦权释放，另一端留在原群。页面始终提示“尚无音频”；这里检查控制流程，不是听测。

同一浏览器的普通标签共享身份存储，不能当成两位成员。刷新后读取后台状态，恢复时不自动按麦。关闭服务再启动，群/成员/当前群保留，麦权清空。单数据目录只允许一实例；正常退出释放锁，异常退出的锁需人工核实，不能同时启动两个进程修改快照。

## 验证

在 `server/`：

```sh
go test -race ./...
node --test internal/httpapi/web/*.test.js
```

服务测试覆盖 HTTP 与状态并发/持久化语义；浏览器测试覆盖松手早于授权、旧响应和切群确认等状态。手工浏览器验收补充布局、指针取消与双身份交互。不要运行 `reference/rta-browser/` 的旧命令来冒充此实现的验证。

## 按切片推进

| 顺序 | 交付物 | 完成条件 |
| --- | --- | --- |
| S1 当前 | Go 控制面、浏览器、身份/群/版本/麦权 API | 契约与状态测试通过，两身份控制流程可运行 |
| S2 无板 | WebRTC 媒体契约、浏览器实音频、服务端门控 | 浏览器双向、一对多、抢麦、跨群隔离和断线实听通过 |
| S3 接板后 | 固件群客户端与生命周期管理 | 板↔浏览器同样验收；保留配网/NVS/已恢复 RTA |
| S4 | 明确群名的主动语音切换与恢复 | 操作终态、目标 RTC 可用、异常与十次切换验收 |
| S5 增强 | 按需求推荐协作群与确认 | 独立模型证据、候选权限、过期/重复确认验证 |

先 S1/S2，再由用户安排接板；不为等待硬件阻塞软件工作。S2 前先补媒体接口，不能把 RTA AI 音频桥当群转发。真机指标用实际测试确定，不预报延迟或资源结论。

## 变更与文档约定

- 产品体验在 `product.md`，组件边界在 `architecture.md`；接口写入 `specs/` 对应切片，不复制多套字段。
- `acceptance.md` 保存当前结论、测试命令、提交/PR 证据。编译、控制状态、实音频分别验收。
- 每个可独立评审的变更保留分支/PR；不覆盖参考工程或改写 `v0` 来源清单。
- `work/` 放运行数据与临时文件；凭据不写源码，不提交构建产物。
- 继续轻量规格驱动。现阶段无需引入 spec-kit；后续若引入，用独立 PR 映射已有规格，保留单一权威入口。

板端构建说明仍在 `firmware/esp32-s31-rti/`。本轮不执行烧录或串口检查；后续先核对已验收提交，再单独安排硬件验证。
