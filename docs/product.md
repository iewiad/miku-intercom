# 声路同行：产品定义

状态：讨论稿，2026-10-23。用户要求先明确产品；尚未确认最终主场景。以下以自驾车队作为建议方案，开发时不得把建议写成用户已确认的决定。

## 产品主张

给结伴出行的自驾车队一台独立语音对讲终端。通过口令加入车队，按住按钮向当前群讲话，通过语音在已加入的群之间切换，减少拿手机找群与切群的操作。

赛题原文面向司机但不限于司机。活动现场、户外徒步、工作调度曾作为候选讨论；当前建议回到司机的车队出行场景。场景尚待用户确认，功能底座不依赖场景名称。

## 谁在什么时刻使用

周末几辆车结伴出行。领队在出发前建立“全队群”和“后勤组”，把口令分享给成员。成员在停车准备阶段输入口令加入需要的群。途中默认在全队群收听；按住大按钮说“前方路口集合”；需要协调物资时，触发语音指令，说“切到后勤组”，确认恢复后再按住说话。

核心问题是跨车辆沟通与快速切换沟通对象。首版使用现有 Wi-Fi / 手机热点联网；实际道路网络、蜂窝模块、导航、定位与车辆控制均没有验收依据。

## 首版闭环

1. 浏览器建群，显示可分享的口令；板端和浏览器使用口令加入。
2. 可以加入多个群，但任意时刻仅收听和发言于一个当前群。
3. 按下 PTT 申请发言权，服务端确认后才发送麦克风音频。一群一人发言；松手、取消、切群、失联即停发。
4. 用户明确触发语音切群，等待“请说群名”，再说“切到后勤组”。使用现有 RTA 的最终用户转写，只允许切换已加入且有权限的群。
5. 后台确认当前群、目标群 RTC 恢复后显示成功。未知群、无权限、超时、重复或迟到结果不误切；失败回到原群，状态不明先查询后台。
6. 显示当前群、成员、发言人、连接与操作状态；断线后恢复为未按麦状态。

## 板端交互

800×480 触屏首页保持当前群、连接状态、发言人和大面积“按住说话”按钮。次要入口为“群列表 / 口令入群”和“语音切群”。建群放浏览器，减少设备输入。成员资格由服务端保存并验证。

语音指令采用单 Peer 串行复用的待验证方案：释放麦权并清空群音频 → 暂停群 RTC → 建立已有 RTA RTC → 接收最终转写 → 服务端确认切群 → stop RTA → 恢复当前群 RTC。过程中会暂时听不到队友，必须明确显示。启动 RTA 的欢迎语应在指令模式取消。未经实测不能承诺无缝切换或具体延迟。

## 明确边界

- 首版采用半双工，不做多人同时讲话。
- 普通群语音由独立对讲服务转发，不经过模型。RTA 仅承担明确触发的语音指令转写。
- 语音不用于绕过口令加入新群；群名称必须唯一或有唯一别名。
- 先不扩展地图、导航、App、录音中心、任务系统、复杂角色和后台管理。
- 题目使用“灵矽应用”措辞，但材料未指定 Provider、WSS、模型或强制 SDK。现阶段沿用用户已确认的 RTA 和历史跑通模型；端侧/SDK的赛事解释仍需记录核实。

## 演示与验收

用一块 ESP32-S31-Korvo-1 加两个浏览器模拟三辆车；如果找到第二套音频板，再补设备互通。

演示主线：建两个群 → 口令加入 → 板与浏览器双向对讲 → 同时抢麦只有一人获权 → 板端语音从全队群切到后勤组 → 新群可对讲、旧群听不到 → 无效群名保持原群 → 断网后可恢复。

硬件验收必须实际听清双向声音，核对发言权和跨群隔离。记录“触发到可说指令”“说完到群音频恢复”的耗时，并连续切换至少十次检查崩溃、泄漏、残留音频与占麦。自动化协议测试不能替代此验收。
