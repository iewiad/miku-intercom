# 声路同行：产品定义

首版产品定义，2026-10-23；交付口径更新于 2026-10-24。面向小组即时协作，不限定车队。本稿规定用户体验，实际进度与证据统一见 [acceptance.md](acceptance.md)，完整演示操作见[演示与收尾指南](demo.md)。

## 定位与主张

**声路同行，面向小组即时协作的智能语音对讲工具。**

**让分散的小组随时沟通，需要协助时，一句话找到对的组。**

产品价值：少操作、找对人、少打扰。首版以“快速组队、按住就说、按群名切换”完成基础闭环；“按需求找到对应小组”作为已纳入规划、尚待验证的增强能力。

帮助需要频繁、简短沟通的小组快速建立语音联系。成员通过嵌入式终端或浏览器进入群，始终知道自己在哪个群、当前发言状态，以及何时可以开麦。语音用于切换沟通对象，也可探索根据用户需求推荐协作小组。普通对讲音频不需要交给模型。

活动执行、户外结伴、车队出行、现场协作均可使用同一套核心能力。它们是使用示例，不是不同版本，也不要求增加行业功能。产品概念中的“小组”不新增一层组织管理系统：首版数据对象仍是群、成员、当前群与发言权。

## 用户、问题与收益

| 用户 | 当下要完成的事 | 产品提供的帮助 |
| --- | --- | --- |
| 发起人 | 临时把分散的人组织起来 | 在浏览器建群并分享短口令 |
| 成员 | 快速向当前协作对象说一句话 | 独立终端上的大面积 PTT，当前群始终可见 |
| 需要跨群协作的成员 | 在全员和专项协作对象间切换 | 明确触发语音切群，不必逐个查找群 |
| 需要协助但不知道该找哪个群的成员 | 表达问题，找到能处理这类事情的小组 | 根据已加入群的职责推荐对象，经确认再接通；增强项待验证 |
| 网络中断后重新上线的人 | 知道自己是否已经恢复沟通 | 显示连接和恢复状态，恢复后保持未按麦 |

首版重点是“建立联系快、发言对象清楚、切换结果可信”。商业需求、复用频率、真实移动网络和付费意愿尚未验证，不能将候选场景写成已经验证的市场结论。

## 范围与默认设计

已确认的必交能力：建群与口令入群、嵌入式 PTT 群内对讲、语音切群、基本状态与恢复。采用半双工，一群一个发言权；普通群音频通过独立 Go 对讲服务转发，原有 RTIC / RTID 与已跑通的模型接口继续复用。

以下作为首版默认设计，随产品评审修订：

| 项目 | 首版设计 |
| --- | --- |
| 角色 | 发起人、成员；不做复杂组织和管理员体系 |
| 建群入口 | 浏览器；输入唯一群名，生成 8 位可分享口令，创建者自动加入 |
| 加入方式 | 设备或浏览器输入口令；后台确认成功才算已加入 |
| 多群 | 可加入多个群，同一时刻只在一个当前群收发 |
| 加入后的去向 | 第一个群自动进入；再次加入新群只保存成员资格，不打断当前对讲，可另选“进入” |
| PTT 操作 | 首版使用已有触屏大按钮，按下申请、获权开麦、松手结束；暂不新增物理按键驱动 |
| 抢麦规则 | 先获权者发言，其他人看到忙状态；不自动排队，避免稍后突然开麦 |
| 语音操作 | 点击“语音切群”后再说话；不常开监听普通聊天里的切群指令 |
| 可切换对象 | 后台确认已加入且仍有权限的群；首版演示服务内群名唯一 |
| 保存与恢复 | 记住设备身份、已入群和最后当前群；重启/重连后向后台核实有效状态，再恢复当前群 |
| 终端组合 | 一块 ESP32-S31-Korvo-1 + 两个浏览器先验收；第二块板单独补验证 |

短口令只用于取得成员资格，终端的随机身份凭据负责后续鉴权；昵称和群名不能代替访问权限。具体控制契约见 [002-control-api.md](specs/002-control-api.md)。当前首版呈现控制状态与已入群成员总数；在线状态尚未实现，不能据成员数推断当前有人在线或能接听。在线人数可作为后续独立增强，不属于需求推荐 S5 的前置条件。

## 按需求找到对应小组（增强规划）

用户不一定记得群名。例如，主动进入语音操作后说“设备坏了，找个能维修的人”，系统根据已加入群的用途推荐“维修组”，显示职责与推荐理由，用户确认后接通。活动、户外或车队可以配置不同职责，核心流程不变。这里的“找人”落实为找到对应小组，不保证具体成员一定在线、空闲或已经接听。

流程：

1. 发起人为群补充可选职责简介，例如“维修组：设备排障”“后勤组：物资、交通、用餐”。这些简介是参考数据，不是模型或后台可执行指令。职责简介不是首版建群必填项。
2. 用户明确触发语音操作并表达需求；推荐环节仅使用本次需求与后台给出的已加入且仍有权限的候选群及必要简介。普通群聊保持直接转发，不常开分析。
3. 在候选范围内给出建议，显示目标群和简短理由。群名不明确、输出不能对应候选群或没有合适对象时，不自动切换；存在多个合理对象时让用户选择。
4. 用户在现有触屏上明确选择并点击“确认进入”。推荐本身不改变当前群；确认前取消或建议失效时，核实并恢复当前群。确认后已提交的请求仍遵守终态确认规则。直接说“切到后勤组”的首版指令仍沿用原有执行流程，不额外套用推荐确认步骤。
5. 确认时后台重新校验权限、目标群和推荐有效性，再复用既有切群执行、幂等请求、终态确认与音频恢复。只有后台确认且目标群音频可用才反馈接通。

模型只参与推荐，对讲服务决定是否执行。推荐输出按不可信内容处理；不假定实际 RTA Profile 支持 tools、function calling、结构化输出或可靠的置信度分数。现有链路能否稳定给出可验证推荐，需要单独验证；不能用助手说“已接通”作为执行证据。

增强项验收：需求能正确推荐已授权群；含糊或无匹配时不误切；未确认不切；确认时权限已变则拒绝；重复、迟到或过期推荐不触发切换。若稳定性未达到要求，保留明确群名切换，不影响首版必交闭环和演示。此增强项没有新增成员搜索、跨权限搜群、自动入群或按个体状态找人的范围。

## 从第一次打开到开始对讲

1. 发起人在浏览器创建“全员群”，分享口令；如需要跨群协作，再创建“后勤组”。
2. 设备沿用现有 Wi-Fi 配网。联网后尚未入群，显示“输入口令加入”，不显示可用的 PTT。
3. 输入正确口令后，后台确认群名及成员资格；第一个群自动连接，设备显示当前群。
4. 首页显示当前群、连接和发言状态；浏览器另显示“已加入成员 3 人”。媒体就绪后成员按住大按钮。
5. 设备显示“正在申请”；服务端授权后提示自己讲话，此时才传输麦克风。其他成员收听音频；浏览器显示持麦者昵称，板端首版不展示其他持麦者身份。
6. 松手、触摸取消、页面隐藏、断线或切群均结束当前发言。群忙时浏览器显示持麦者，板端未获权则提示松手重试；不会排队自动开麦。
7. 通过群列表输入另一个群的口令，保存新成员资格。用户主动选择进入，或以后通过语音切换。

昵称只用于显示，不能作为鉴权身份。已入群成员总数包含离线成员，不表示当前在线人数。

## 设备页面与状态

800×480 触屏首页只保留信息与操作的主次关系：

- 顶部：当前群名、服务连接状态。
- 中部：连接与本机发言状态，包括可发言、正在申请、自己讲话和未获权重试；成员总数与其他持麦者由浏览器展示。
- 主操作：大面积“按住说话”。
- 次操作：“群列表”“语音切群”。
- 状态反馈：操作中的等待、失败原因和重试入口。

| 状态 | 用户看到什么 | 可用操作 |
| --- | --- | --- |
| 未联网 | 需要连接 Wi-Fi | 沿用配网入口 |
| 已联网、未入群 | 输入口令加入 | 入群 |
| 连接当前群中 | 群名 + 连接中 | 取消或重新连接；PTT 不可用 |
| 群内空闲 | 当前群、连接就绪、可发言 | PTT、群列表、语音切群 |
| 正在申请发言 | 正在申请 | 松手取消；未获权不发送音频 |
| 自己讲话 | 你正在讲话 | 松手结束 |
| 他人讲话 | 浏览器显示持麦者；板端保持收听，申请未获权则提示重试 | 收听；松手后重新按麦尝试 |
| 语音切群中 | 准备/请说群名/确认/恢复 | 请求提交前可取消；提交后等待确认；PTT 不可用 |
| 连接异常 | 当前群 + 连接失败/正在恢复 | 重试、群列表；PTT 不可用 |

浏览器兼任发起人入口和成员终端，使用同一套群与发言规则。首版无需单独开发手机 App。

## 语音切群体验

用户点击“语音切群”，系统释放当前麦权、停止群音频，显示“正在准备语音指令，暂时无法收听群聊”。准备好后提示“请说目标群名”，例如“切到后勤组”。

首版只处理最终用户转写中的明确群名命令；按需求推荐遵循上一节的独立确认规则。服务端执行有限命令匹配并核验成员资格；普通聊天不能触发切群，语音不能绕过口令加入新群。首次最终结果提交后，本次指令不再接收新的切换请求，旧会话或重复结果均无效。

先显示“正在切换到后勤组”。请求提交前可以取消；提交后改为等待确认，不提供撤销。**该请求已到终态、后台确认当前群且目标群音频连接恢复后**，才显示“已进入后勤组，可以对讲”。成功反馈不能只依据转写文本，也不能只依据 HTTP 请求已发送。

首版采用单 Peer 串行复用：退休群 RTC → 原 RTA RTC 取最终转写 → 明确群名解析 → 原切群操作与 RTA 终态确认 → 恢复群 RTC。板端先结束 RTA 再提交切群，浏览器先持久提交并确认控制操作再结束 RTA；未确认期间都不重建群 Peer。指令阶段关闭欢迎语。该路线存在暂时听不到队友与重连等待；必须先实测，不能承诺无缝切换或具体延迟。

## 失败与恢复

| 情况 | 行为和反馈 |
| --- | --- |
| 口令错误 | 不加入，提示检查口令；当前群不变 |
| 未识别、未知群、无权限、目标含糊 | 不提交切群或由后台明确拒绝，结束指令并恢复原群 |
| 指令无结果/提交前取消 | 停止 RTA，核实后台当前群，再恢复连接；不会产生待生效切群请求 |
| 请求已发出但结果超时 | 显示“正在确认切群结果”，查询对应请求终态和当前群；只有该请求已完成或后台保证其不再生效，才按确认状态恢复，避免查询后迟到切群 |
| 后台已切成功，但目标 RTC 失败 | 显示目标群和“连接失败，重试”；不得错误显示还在原群或已可对讲 |
| 普通断网 | 立即停发、清理旧音频与麦权，显示离线；网络恢复后核实并连接当前群 |
| 进程/设备重启 | 恢复保存的身份，核实有效成员资格与当前群；无有效身份时回到入群 |
| Peer 清理失败 | 不启动第二个 Peer；执行有界恢复并提供重新连接 |

所有恢复都回到未按麦状态。客户端停发与服务端麦权租约共同避免失联后占麦；收到旧群音频不能带入新群播放。

## 首版边界

不扩展地图、导航、录音中心、车辆控制、行业任务、手机 App、多方同时讲话或开放式语音助手。先验证通用对讲与按群名切换，再评估已规划的受限需求推荐。

题目写“灵矽应用”，材料没有指定 Provider、WSS、模型或强制 SDK。用户已确认沿用原 RTA 和已跑通模型；现有集成如何对应赛事的“灵矽应用”口径仍需解释核实，不能由语音转写可用直接推导满足品牌要求。

## 演示设计与验收

产品跨场景，演示选择一个“临时活动协作”例子：三个成员分别使用板端、浏览器 A 和浏览器 B，在“全员群”和“后勤组”交流。演示场景可以换成车队或户外，产品流程无需改造。

下表是目标脚本；分项听测和触控通过不代表已按此顺序完成整场录制，操作与通过判据见[演示指南](demo.md)。

| 时间 | 目标演示（完整串联待验） |
| --- | --- |
| 0:00–0:30 | 浏览器建群、板端口令加入，三个端看到当前群，浏览器显示已加入成员数 |
| 0:30–1:20 | 板↔浏览器双向实音频；短暂同时抢麦，仅一人获权 |
| 1:20–2:10 | 板端说“切到后勤组”，恢复后与 B 双向对讲；A 留原群，确认听不到新群语音 |
| 2:10–3:00 | 无效群名不误切，恢复后返回全员群；说明普通对讲不经过模型 |

增强能力通过独立验收后，可加演“说出需求 → 推荐对应群 → 明确确认 → 连接后实际对讲”；基础演示不依赖该能力。

另行做断网/重连、触摸取消、重复/迟到结果和权限拒绝验证。记录“触发到可说指令”“说完到群音频恢复”两个耗时，连续切换至少十次检查崩溃、持续资源下降、残留音频和占麦。耗时目标由首次真机测量后决定。

一块板加两个浏览器不等于两块设备互通；第二块板需单独实测。原 RTA 可用也不代表群音频成立，各项结果只在[验收记录](acceptance.md)维护。

## 推进次序

1. 先完成独立服务与浏览器的身份、群、成员资格、当前群、发言权控制状态；不连接板子、不调用 RTA。
2. 冻结媒体契约并在浏览器间验证群实音频、服务端门控、跨群隔离与恢复。
3. 用户安排接板后验证板↔浏览器 Opus/SDP/ICE，接入 PTT 和群状态。
4. 接入原 RTA 最终转写、明确群名切换与单 Peer 恢复；验证终态、资源与实际停顿。
5. 基础闭环可靠后独立验证需求推荐，再按演示脚本验收、录视频并完善交付材料。

功能与验收条件见 [MVP 规格](specs/001-intercom-mvp.md)，运行和测试见[开发指南](development.md)。采用轻量规格驱动，不为等待硬件阻塞软件开发，也不把控制演示算作音频完成。

开发截止为 2026-10-26 09:00（Asia/Shanghai）。复用基线已在新增对讲代码前以远端 `v0` 留存，逐文件记录见 [v0-manifest.json](v0-manifest.json)。
